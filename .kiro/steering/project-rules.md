# 项目开发规则

## 核心原则

### 严格遵循用户指示
- 严格按照用户指示行动，不乱改用户配置好的模型、不错改格式字符、不瞎改代码，不自己造轮子
- 不破坏文件结构
- 出现问题后绝对不能直接用错误的备份文件覆盖替换，要等待用户命令
- 绝对不能大量删除或改动代码，除非用户明确指示
- 如果命令提示错误一次则不再使用错误的命令，除非用户再次指示

### 代码修改原则
- 做最小化修改，不要全部替换
- 局部修正，保持现有结构
- 验证信息后再做修改
- 保留现有代码结构

### 沟通原则
- 不要道歉
- 不要感谢
- 像人一样交流
- 提供简洁相关的回复
- 交互使用中文

## 代码质量

### DRY (Don't Repeat Yourself)
- 代码复用，避免重复
- 任何逻辑只写在一个地方

### KISS (Keep It Simple Stupid)
- 保持简单，避免不必要的复杂性
- 简单代码更易理解、调试和修改

### YAGNI (You Aren't Gonna Need It)
- 只实现当前需要的功能
- 不要基于预测过度设计

### 单一职责
- 每个实体（类、函数、变量）只做一件事
- 代码应该易于阅读和理解

## 禁止事项

- 跳过思考步骤
- 添加占位符或 TODO
- 交付非生产就绪的代码
- 移除/修改代码时不知道如何恢复相同功能
- 破坏现有功能

## 项目特定规则

### Supabase 集成
- 使用 `var _sbClient` 而不是 `let supabase` 避免和 CDN 全局变量冲突
- 所有 AI 功能必须有扣费逻辑
- 必须登录才能使用，不能白嫖

### 部署
- 部署命令: `vercel deploy --prod --yes`
- 用户域名: www.rollroll.art
- 全部修好再部署，不要每次没修好就部署

### 移动端支持
- 按钮需要同时支持 click 和 touchend 事件
- 使用 `force=mobile` 参数标识来源

### Specs 管理
- Specs 用完必须删除，保持 .kiro/specs 目录整洁
- 删除 specs 前必须询问用户确认，不能自动删除
