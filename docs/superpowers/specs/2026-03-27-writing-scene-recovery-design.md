# 2026-03-27 AI 写作场景入口修复与写作回归排查设计

## 背景

当前写作页的章节卡片“场景”按钮已经从原本的单次生图入口改成了 storyboard 全流程入口，导致点击后优先走二次 `_novelLLM` 的分镜 JSON 拆分，再拼分镜大图。这个路径虽然保留了结构化分镜能力，但也重新引入了两类核心问题：

1. 二次 LLM 拆分带来的超时、524、流式相关失败。
2. “场景”按钮的行为与用户实际预期不一致。用户要的是“一次生成一张多分镜感图片”，而不是先拆 JSON 再跑后续流程。

同时，用户补充反馈：在长篇小说和短剧功能加入后，原有 AI 写作其他功能出现回归，包括记忆区分不好用、普通生成出现 524、整体稳定性变差。这说明 novel / short-drama 的新增逻辑可能污染了原有共用写作链路，需要在修复场景入口后继续做一次有边界的主流程排查。

## 目标

本次工作分两部分推进：

### 第一部分：恢复稳定的“场景”入口

- 章节卡片“场景”按钮改回单次生图入口。
- 生成结果仍然保持“多分镜感”的视觉效果，而不是退回普通单场景图。
- 复用项目现有故事提示板模板、网格分镜约束思路和角色参考图能力。
- 避免再次走二次 `_novelLLM` 拆分流程。
- 尽量减少对已存在 storyboard 逻辑的影响，不删除旧能力，只取消它作为默认入口的角色。

### 第二部分：排查 AI 写作主流程回归

- 排查普通 AI 写作功能为何在加入 novel / short-drama 后变差。
- 排查“记忆区分”失效或异常的原因。
- 排查 524 的主要来源是否是状态污染、参数污染、上下文膨胀或错误路由。
- 在不大改架构的前提下，优先恢复用户最直接感知到的功能稳定性。

## 范围与非目标

### 在范围内

- `js/novel-features.js` 中“场景”入口与单次生图逻辑修复。
- 复用 `js/prompt-templates.js` 和 `js/batch.js` 中已有多分镜 prompt 思路。
- 使用角色参考图增强一致性。
- 排查普通 AI 写作与 novel / short-drama 之间的共享状态、共享参数与记忆区分逻辑。
- 必要时修复写作页脚本缓存版本号，确保前端不再加载旧逻辑。

### 不在范围内

- 不删除 storyboard 相关函数。
- 不重写整个写作页架构。
- 不顺手做与本次故障无关的大规模 UI 改造。
- 不顺手处理先前发现但当前非最高优先级的安全问题。

## 当前已确认的代码现状

1. 章节卡片“场景”按钮当前调用 `novelStoryboardFullPipeline(i)`，位置在 `js/novel-features.js`。
2. `novelGenerateSceneImage(chapterIdx)` 仍然保留，但当前只生成普通单场景图，不具备多分镜感。
3. `novelGenerateStoryboards(chapterIdx)` 仍然会调用 `_novelLLM(...)` 生成 JSON 分镜数据，是当前超时和流式问题的关键来源之一。
4. `js/prompt-templates.js` 已有可复用模板：
   - `multi_char_comic`
   - `nine_grid_story`
   - `script_storyboard`
   - `consistency_lock`
5. `js/batch.js` 中 `buildGridImagePrompt(...)` 已有成熟的“单张多格 storyboard 图片”提示词骨架，可复用其网格、多格独立画面、角色一致性等约束思路。

## 方案概述

### 方案 A：恢复 `novelGenerateSceneImage()` 为默认入口（采用）

#### 入口调整

把章节卡片“场景”按钮从：

- `novelStoryboardFullPipeline(i)`

改为：

- `novelGenerateSceneImage(i)`

这样点击“场景”后直接走单次生图，不再触发二次 `_novelLLM`。

#### prompt 重构

重写 `novelGenerateSceneImage()` 的 prompt 拼装方式，不再生成普通“宏大场景氛围图”，改为生成：

- 一张图内多个分镜格
- 每格为独立画面
- 整体统一风格
- 保持角色一致性
- 更像工坊故事提示板 / 电影分镜板

prompt 输入来源：

- 当前章节标题
- 当前章节正文前几百字
- 章节摘要或可用概述（如果已有）
- 角色名称与角色描述
- 角色参考图 URL
- 当前类型（短剧 / 非短剧）

prompt 结构来源：

- 复用 `multi_char_comic` 的多角色连续画面概念
- 复用 `nine_grid_story` 的“多个连续画面组成完整叙事”概念
- 复用 `script_storyboard` 的故事板 / 分镜草图表达
- 复用 `consistency_lock` 的角色锁定约束
- 借鉴 `buildGridImagePrompt(...)` 的关键要求：
  - 这是分镜板，不是一张大图切块
  - 每格必须是独立完整画面
  - 统一风格与镜头语言
  - 角色外观在多格中保持稳定

#### 比例策略

按章节类型自动选择比例：

- 短剧：`9:16`
- 其他类型：`16:9`

这样避免让用户手动切换，也符合用户已确认的预期。

#### 角色参考图传入

如果当前已有角色图：

- 收集角色 `imageUrl`
- 作为 `refImages` 传给 `callBanana2ImageAPI(...)`
- 同时在 prompt 中明确“角色一致性参考”要求

如果当前没有角色图：

- 仍允许生成
- 但只使用文本角色描述约束，不阻断功能

#### 兼容性策略

保留以下函数但不删除：

- `novelGenerateStoryboards()`
- `_novelGenerateStoryboardPanel()`
- `novelStoryboardFullPipeline()`

这样做的原因：

- 最小化改动范围
- 避免误伤已有依赖或未来备用入口
- 把这次修复集中在“默认入口纠偏”而不是“重构分镜系统”

## AI 写作主流程回归排查设计

在完成“场景”入口修复后，继续排查写作主流程回归，范围聚焦为 4 类问题。

### 1. 状态污染排查

重点检查：

- 写作页是否把 novel / short-drama 的状态写进了原本普通 AI 写作共用状态。
- localStorage key 是否复用、覆盖或串线。
- 页面模式切换后是否残留 novel 特有状态并影响普通写作。

目标：

- 普通 AI 写作、长篇小说、短剧三类流程的运行态互不污染。

### 2. 参数污染排查

重点检查：

- `_novelLLM`、普通写作 API 调用、通用生成入口是否共享了错误参数。
- `stream`、`timeout`、`maxTokens`、模型选择、消息体结构是否误复用。
- 是否存在将 novel 的超大上下文或特定 message schema 带入普通写作的情况。

目标：

- 普通写作回到原本轻量、稳定的调用参数。

### 3. 记忆区分异常排查

重点检查：

- 写作页中“记忆区分”依赖的当前模式、上下文来源、缓存键和 UI 状态。
- 是否在 novel / short-drama 接入后，模式判断发生串线。
- 是否出现普通写作误读 novel 记忆、或 novel 误用普通写作记忆的情况。

目标：

- 让不同写作模式使用各自正确的上下文与记忆来源。

### 4. 524 根因排查

重点检查：

- 524 是否集中出现在普通写作内容生成，而不是小说特定流程。
- 请求上下文是否在接入 novel / short-drama 后明显膨胀。
- 是否因超长请求体、错误模型、错误超时设置、错误流式设置造成等待超时。

目标：

- 优先修复最明显、最直接的超时根因，而不是泛化地“优化所有请求”。

## 实施顺序

1. 修改“场景”按钮入口。
2. 重写 `novelGenerateSceneImage()` 的 prompt 和参考图逻辑。
3. 验证该入口不再触发二次 `_novelLLM`。
4. 验证短剧 / 非短剧比例自动切换。
5. 再开始排查普通 AI 写作回归问题。
6. 修复最明确的状态污染 / 参数污染问题。
7. 必要时提升写作页脚本版本号，确保缓存更新。
8. 完成验证后再执行 CLI 部署。

## 验证方案

### 场景入口修复验证

至少验证以下几点：

1. 点击章节卡片“场景”后直接走 `novelGenerateSceneImage()`。
2. 不再调用 `novelGenerateStoryboards()` 触发二次 `_novelLLM`。
3. 短剧章节生成 `9:16` 分镜感图片。
4. 非短剧章节生成 `16:9` 分镜感图片。
5. 有角色图时请求体包含参考图。
6. 生成结果仍为单张图，但具有明显多分镜感。

### AI 写作回归验证

至少验证以下几点：

1. 普通 AI 写作功能可以正常生成内容。
2. 记忆区分恢复到可感知正确状态。
3. 不再明显复现此前用户提到的 524。
4. 长篇小说 / 短剧功能不因这次修复被破坏。

## 风险与控制

### 风险 1：只改按钮入口但旧渲染区域仍引用旧数据

控制：

- 保留 `_storyboards` 相关渲染逻辑不动。
- 新入口仅影响默认点击路径，不强制清理旧数据结构。

### 风险 2：新 prompt 过重导致单次图片生成依然超时

控制：

- prompt 使用现有模板思路，但不照搬过长结构。
- 只取章节前几百字和核心角色信息，避免上下文过长。
- 优先用“强约束 + 精简内容”的方式生成。

### 风险 3：写作回归问题范围过大

控制：

- 先聚焦状态污染、参数污染、记忆区分、524 四类问题。
- 只修复有直接证据的回归点，不展开全局重构。

## 决策记录

- 用户已确认“场景”比例采用按类型自动选择：短剧竖版，其他横版。
- 用户明确要求单次出图、多分镜感、复用工坊故事提示板思路，不要再走二次 LLM。
- 用户要求完成后部署更新，因此部署不是单独任务，而是本次交付链路的最后一步。

## 预期结果

完成后，用户应能获得以下行为：

1. “场景”按钮再次稳定可用。
2. 点击后直接得到一张多分镜感图片，而不是先经历结构化拆分流程。
3. 角色一致性比普通单图更稳定。
4. AI 写作普通功能不再被小说 / 短剧逻辑反向影响。
5. 生成失败和 524 的概率明显下降。
6. 在验证通过后，使用 CLI 完成部署更新。
